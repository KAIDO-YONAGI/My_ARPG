# 多 Agent 工作流指南

文档 ID：`WF-GUIDE`  
状态：`Active`  
维护计数：`0/5`  
最后更新：`2026-10-05`

## 路由

按任务词、目标路径、运行资源和预期结果路由。任务描述用来定位分类，实际行为来自该分类的
Guide/Design。跨业务任务要进入每一个受影响的业务根。

## 业务根

先复用已有分类，再考虑新建。新增顶级分类与工作区级规则必须取得用户确认。每个业务根至少
包含 `Router.md` 与 `DeveloperLog.md`。

## 深度

工作流根以下的目录层级不得超过五层。到第六层之前，要么提升为独立子类，要么合并重复层级，
要么改用 Router 标签。

## 文档写法

Guide、Router 与 Proposal 按当前状态陈述事实，读者据此判断系统现在如何工作。

- 只写现在成立的事。内容失效就改写或删除，不标注来历，不追溯变化。
- 不写资产路径，也不写资产文件名：资产按名称与职责描述。资产改名、移动、重做后文档依然成立。
- 不写代码路径与行号：代码按类型名与方法名描述，编辑代码不会让文档失效。
- 工程配置、工具脚本与文档的路径可以写。验证与构建命令必须能照着执行，不留占位符。
- 结论用正文讲清楚，不用括号附注。
- 直接写成立的那一面，少用否定与转折句式。
- 同一事实只在一处展开，其余位置引用文档 ID。

DeveloperLog 是日志，保留时间线追述。需要判断某条结论的来历和被推翻的过程时读它。

## 写法自查

`Workflow\Scripts\Check-DocStyle.ps1` 逐文件检查上面的规范，发现 error 时退出码为 1。
改动文档后先运行它，再运行结构校验。

## 维护

只有成功且实质影响某业务根的任务才让它的计数 +1。失败、取消、租约记账、只读取证和纯文档
维护都不计入。到 `5/5` 时对照证据与工程实际状态复核，更新权威文档或记录
`reviewed-no-change`，然后清零。

不要自动截断 `DeveloperLog.md` 历史。只有用户明确确认某条目冗余或过时后才能删除，否则
保留全部条目。

`workflow:<业务根>` 只在写 Router/Log 时使用，`workflow:root` 只在根结构变更时使用。
