# UI 改造方案

> 方案与进度 · 2026-10-31 · 非权威文档；第 1 步已接入属性面板，其余待实施

沿用现有 `UIManager`，补上界面缓存、模态弹窗栈和循环列表。界面内部继续采用项目已有的 MVCS/MVP 思路，先接入属性面板与任务列表，再迁移商店和背包。

## 1. 界面注册与缓存

**配置负责找到预制体，缓存负责复用实例。** 启动时登记“界面 ID → Prefab 与显示策略”；首次打开才创建实例，之后优先复用。

```text
打开：查找定义 → 取缓存，未命中则创建 → 绑定数据并显示
关闭：解除订阅与回调 → 隐藏实例 → 放入闲置缓存
清理：超过缓存上限 → 销毁最久没有使用的闲置实例
```

LRU 用字典配合双向链表实现：字典定位实例，链表维护使用顺序。正在显示的界面不参与淘汰；常驻 HUD 单独保留。首版按闲置实例数量限制缓存，资源加载先使用 Prefab 直接引用。

**已落地：** `UIManager.cachedViewPrefabs` 登记预制体，`UIViewCache` 按事件资产的 `CanvasToToggle` 创建和复用实例。属性面板已提取为 `Assets/Prefabs/UI/Runtime/StatsCanvas.prefab`；常驻场景通过 `RuntimeViews` 承载实例。`maxIdleViews` 默认 3，设为 0 则关闭即销毁；切场景时清空缓存。直接引用的 Prefab 及其贴图等资源仍然保留，淘汰仅销毁界面实例。

项目现有 `ObjectPool<T>` 适合重复借还同一种对象；界面缓存还要处理界面身份、显示状态和淘汰顺序，因此单独实现。关闭后的 View 停止刷新，任务进度、背包内容等业务数据继续由业务层持有。

## 2. 弹窗栈

**普通窗口可以点击后提到前面，模态弹窗按后进先出关闭。** 现有 `CanvasFocusStack` 保留，用来处理普通画布；新增 `ModalStack` 管理弹窗实例。

在常驻场景中增加专用 `ModalRoot`。每次打开弹窗都放入该节点并入栈，关闭时只关闭栈顶，再恢复下层的交互和选中控件。相同类型的弹窗可以多开，用实例句柄区分。

需要一起落实的规则：

- 只有栈顶响应点击、键盘和手柄导航；遮罩拦住底层界面。
- ESC 一次只关闭一个弹窗；栈顶禁止关闭时，ESC 不向下传递。
- 死亡界面请求优先处理，先取消弹窗；切场时统一关闭，清除旧场景引用。
- 按钮、ESC、切场即使连续触发，同一个弹窗的结果回调也只执行一次。

弹窗排序放在普通窗口之上、场景过渡遮罩之下。`UIManager` 负责输入分派，模态栈负责顺序，弹窗 View 只负责显示和返回操作结果。

## 3. LoopList 与 LoopGrid

**数据可以很多，UI 节点只保留视口附近需要的数量。** 例如有 1,000 条任务，屏幕显示 8 行，就只维护十来个 cell，而不是创建 1,000 个。

滚动时根据偏移计算可见索引：离开视口的 cell 解绑，进入视口的条目复用空闲 cell；仍在视口内的条目不反复刷新。列表和网格共用这套逻辑，只改变每行列数和坐标计算。

首版支持固定行高的纵向列表、固定格尺寸的纵向网格。控件基于 `ScrollRect`，自己管理 Content 尺寸和 cell 位置，避免与 LayoutGroup 重复计算。

复用时必须重新绑定文字、图标、完成态、选中态和点击目标；解绑时清理监听与提示框。**cell 是显示容器，不能成为业务数据的存储位置。**

## 4. 界面内部分工

MVC 把模型、显示、控制分开；MVP 进一步由 Presenter 协调数据和 View；MVVM 则通过属性与命令绑定驱动显示。本项目已有 `PlayerStatsModel → StatsCanvasController → StatsCanvasView`，继续沿用这套方式即可。

| 层 | 负责什么 | 项目中的例子 |
|---|---|---|
| Model / Service | 保存状态、执行规则、提供读写入口 | 玩家属性、任务进度、购买结算 |
| Controller / Presenter | 接收界面操作，调用业务命令，把数据转换成显示内容 | 选择任务、刷新任务详情 |
| View | 持有控件、显示数据、上报点击 | 标题、图标、按钮、列表行 |

打开时绑定并首刷，关闭时退订；淘汰后重建 View，业务状态仍然存在。现有 Controller 名称保留，首版不引入 MVVM 绑定框架。

## 5. 在项目中怎么落地

`UIManager` 继续作为入口，组合三个独立职责：`UIViewCache` 管实例复用，`ModalStack` 管弹窗顺序，`LoopList/LoopGrid` 管可见条目。通用组件放在 `Assets/Scripts/Pipeline/UI/`，业务适配代码放回各自的 `Gameplay` 目录。

| 顺序 | 改动 | 做完应看到什么 |
|---|---|---|
| 1. 属性面板 | 提取 Stats Prefab，增加注册与缓存；调整 StatsCanvasView/Controller 的绑定生命周期 | 关闭再开复用实例；淘汰后重建仍显示当前属性 |
| 2. 确认弹窗 | 增加 ModalRoot、实例栈和通用确认框，接入 UIManager 的输入与切场流程 | 两个弹窗可以嵌套，只有栈顶可操作，关闭后恢复下层 |
| 3. 循环容器 | 实现共用的可见区计算与 cell 池，再提供列表和网格入口 | 1,000 条数据也只创建视口附近的节点，滚动不串数据 |
| 4. 任务列表 | 用 Controller 适配任务数据，替换固定 QuestLogSlot 数组的显示流程 | 超出原槽位数量仍可浏览；完成态随复用正确恢复 |
| 5. 商店、背包 | 先解除业务数据对 UI 槽位的依赖，再接循环网格 | 回收显示格不会改变商品价格或背包内容 |

迁移时有三个必须先处理的项目问题：

- **任务：** 进度留在常驻 `QuestManager`；列表绑定只读状态。当前选择任务会进入状态处理链，需要把展示与完成命令分开，避免刷新或滚回条目时重复发奖。
- **商店：** 卖价目前从 `ShopSlot` 查找。改为查询商品数据后，滚出视口的商品才不会失去报价。
- **背包：** 物品和数量目前保存在 `InventorySlot`。先拆出独立槽位模型，保留快捷栏优先、堆叠、使用和丢弃规则，再复用显示格。

## 6. 验收重点

1. **缓存有效：** 命中时不重复创建，超过上限只淘汰闲置界面，关闭后没有残留订阅。
2. **弹窗可靠：** 输入不穿透，一次关闭一个，死亡和切场能收尾，回调不重复。
3. **列表正确：** 节点数随视口大小变化；快速滚动、增删、重排后，内容与点击目标一致。
4. **业务完整：** 重建界面不丢进度、不改背包、不重复领奖；原有面板快捷键、焦点和互斥行为正常。

实施按上述顺序分批进行。第 1 步已完成代码与场景接线，并通过 Unity 编译及引用检查；运行时复用和多界面淘汰尚未验证。其余步骤仍是方案。
